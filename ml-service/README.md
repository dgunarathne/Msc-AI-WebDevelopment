# EVCircle ML Service

FastAPI + scikit-learn microservice providing the 4 AI/ML features for EVCircle:

- `POST /predict/wait-time` — queue/wait-time forecasting (GradientBoostingRegressor)
- `POST /predict/range` — EV range/consumption prediction (RandomForestRegressor)
- `POST /recommend/stations` — context-aware station ranking (weighted scoring, not a learned ranker — see below)
- `POST /route/plan` — energy-efficient route planning with charging-stop insertion (OSRM + range model + scoring)

Laravel (EVCircle) calls this service over HTTP; see `evcircle/app/Services/MlServiceClient.php`.

## Setup

```bash
cd ml-service
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

python scripts/generate_synthetic_data.py
python scripts/train_wait_time_model.py
python scripts/train_range_model.py

uvicorn app.main:app --reload --port 8000
```

## SYNTHETIC DATA — important limitation

EVCircle does not currently capture real charging-session telemetry (no logged
queue lengths, no logged energy delivered — see the dead `ChargingHistory`
relation in `User.php` and the empty `charging_sessions` table this project
adds). Both models are trained on **synthetic data** generated by
`scripts/generate_synthetic_data.py` from domain-assumption formulas:

- **Wait-time**: a simplified M/M/c-style queueing approximation
  (`wait ≈ excess_queue × avg_session_time / free_connectors`) driven by a
  bimodal (morning/evening peak) demand curve, plus Gaussian noise.
- **Range/consumption**: known EV-physics approximations — quadratic
  aerodynamic drag penalty above ~80 km/h, cold-weather HVAC/battery penalty
  below 10°C, linear elevation-gain penalty, and a driving-style multiplier —
  plus Gaussian noise.

Holdout R² for both models is intentionally high (~0.95) because the targets
are themselves generated from smooth formulas — **this reflects the models
recovering the synthetic generating function, not real-world predictive
power**, and should be reported as a documented limitation, not a strength.
Once `charging_sessions` accumulates real rows in production, retrain both
models against real data using the same scripts (swap the CSV source).

## Recommendation: why no learned ranking model

`/recommend/stations` uses a weighted scoring function (`app/services/scoring.py`)
over distance, predicted wait time, price fit, connector match, and
fast-charging preference — not a separate trained ranker. There is no
ground-truth "this was the correct station to recommend" label anywhere in
the system to train against, so a learned ranker would just be fit to
arbitrary noise. The weighted score is explainable (each recommendation
includes `reasons`) and is the right MVP choice; revisit only if real
click-through/booking-conversion data is collected per recommendation.

## Route planning: known simplification

`/route/plan` (`app/services/route_planner.py`) is a **greedy single-pass**
planner: it walks from origin to destination and inserts one charging stop
whenever projected state-of-charge would drop below a safety margin, picking
the best reachable, forward-progress station. It is not a full multi-stop
graph optimizer (e.g., Dijkstra/A* over a station graph with joint
cost-of-detour minimization) — that is future work if multi-stop long-haul
trips become a priority.

## OSRM

Routing uses the public OSRM demo server (`https://router.project-osrm.org`,
no API key, no SLA). If it is unreachable, `osrm_client.get_route_with_fallback`
degrades to a straight-line Haversine distance with an assumed average speed,
so the route endpoint still returns a usable (if less accurate) result rather
than failing outright.

**Known environment issue**: on some machines with an old system Python built
against LibreSSL 2.8.3, `httpx` fails the TLS handshake against the OSRM demo
server (`SSLV3_ALERT_HANDSHAKE_FAILURE`) even though `curl` succeeds, because
the two use different TLS stacks. If you hit this, run the service with a
Python built against a modern OpenSSL (3.x) instead — verify with:
```bash
python -c "import ssl; print(ssl.OPENSSL_VERSION)"
```
Until then, the Haversine fallback keeps `/route/plan` functional.

For production, self-host OSRM via Docker (`osrm/osrm-backend`) with an
OpenStreetMap extract for your region (EVCircle is Sri Lanka-focused) and
point `OSRM_BASE_URL` at it.

## Config

Environment variables (`.env`, see `app/config.py`):
- `OSRM_BASE_URL` (default: public OSRM demo server)
- `MODEL_DIR` (default: `models`)
- `HOST` / `PORT` (default: `0.0.0.0` / `8000`)
